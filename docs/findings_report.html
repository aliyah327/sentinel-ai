1. Objective

This project evaluates the robustness of a chat model's safety guardrails against prompt-injection and encoding-based evasion attacks, and packages the evaluation as a reusable, installable command-line tool inspired by Promptfoo and Garak.

A deliberate design decision underlies the whole project: rather than measuring whether a model will produce genuinely dangerous content (which would require generating that content to grade it), Sentinel-AI uses a canary-token method. A harmless secret string is planted in the system prompt, and the model is instructed never to reveal it. An attack is counted as successful only when the model leaks that harmless token. This yields the same security signal — can the guardrail be defeated? — with zero hazardous output, so the tool is safe to publish and reuse by other researchers.

4. Root-cause analysis

The target's guardrail is a keyword filter: it scans the raw user text for words like "secret" or "token" and refuses when it finds them. This explains every number above:

  • Plain text (25% ASR): direct requests contain the banned keywords, so most are refused. The few successes come from injection-style phrasings that avoid the keywords.
  • Base64 & ROT13 (100% ASR): the filter sees only an opaque encoded blob — the banned words are not literally present — so the request passes the filter untouched. The model then decodes and obeys it. This is the central vulnerability.
  • Leetspeak (0% ASR): the substitutions perturb the keywords enough to pass the filter, but the target does not "un-leet" the text, so the request is never acted upon. This reveals that filter coverage is uneven across transforms — a finding in itself.
  • Prompt injection (75% ASR): fake "system administrator / developer mode" framing exploits a weak trust boundary — the model treats untrusted user text as if it were a privileged instruction.
Core lesson: input-keyword filtering gives a false sense of safety. Any attacker who re-encodes their request walks straight past it. Robust guardrails must evaluate decoded intent and enforce a trust boundary, not match surface strings.

5. Recommended mitigations

  • Decode-then-check: normalise/decode inputs (Base64, ROT13, leetspeak) before the safety check, so the filter sees the real intent.
  • Enforce a trust boundary: never let user text be promoted to system authority; ignore "ignore previous instructions / admin override" patterns.
  • Output-side canary guard: scan model output for the secret and block it — defence in depth, independent of the input filter.
  • Semantic (model-based) classification instead of keyword matching, for intent that survives re-encoding.

Each mitigation is directly testable by re-running Sentinel-AI after applying it and confirming the ASR for the corresponding strategy drops — the "validate the fix" step from the training's evidence workflow.

6. Validation & reproducibility

Every case in the HTML/JSON report records the exact attack input, the full model response, and the detector verdict, so any finding can be reproduced independently. Four automated tests (tests/test_sentinel.py) lock in the core behaviours as regression checks. The mock target makes results deterministic; the Ollama target runs the identical benchmark against a real local model with all traffic confined to localhost:11434.

7. Conclusion

Sentinel-AI demonstrates, with reproducible local evidence, that keyword-based LLM guardrails are defeated by trivial input encoding (100% ASR for Base64 and ROT13 here) and by trust-boundary violations (75% ASR for prompt injection). The tool is modular, tested, documented, and installable, and it produces this evidence without ever generating harmful content — making it a practical, safe building block for real guardrail-robustness testing.
